# Nav Sylph 监控 agent

部署在**被监控的目标机**上，让 Nav Sylph 服务能读到这台机器的 CPU、内存与负载。

本服务只能读到运行它自己的那台主机。要看别的机器，目标机上就得有一个东西去读
系统计数器并把结果吐出来——这就是 agent 的全部职责。

## 特性

- **静态二进制，零依赖**。一个文件拷过去就能跑，NAS、路由器、精简容器上都不用先装
  Node 或 Python。三个架构：amd64 / arm64 / armv7（armv7 覆盖老树莓派）。
- **只读**。只读系统计数器，不写系统文件。
- **两种上报方向**。拉取（默认，起一个 HTTPS 服务等本服务来连）或推送（`--push`，
  只做出站连接，**不监听任何端口**）。
- **Bearer token 鉴权**。凭据落在权限 600 的 `/etc/nav-agent/` 下，不进 systemd unit。
- **证书自己签发**。用 Go 的 `crypto/x509`，不需要 openssl。

## 前置要求

- **Linux**（amd64 / arm64 / armv7），内核 3.10 以上
- **root 权限**（写 `/usr/local/bin` 与 `/etc/systemd/system`）
- 能访问 Nav Sylph 服务的地址

检查：`uname -m`

> macOS 也能编译（`go build` 会产出一份 darwin 二进制），但**不是受支持的平台**：
> `sysctl kern.cp_time` 在现代 macOS 已被移除，没有 cgo 就拿不到累计 CPU 时间，
> 于是 CPU 一栏恒为「—」。darwin 产物只用于开发机自测。

## 选哪种模式

| | 拉取（默认） | 推送（`--push`） |
| --- | --- | --- |
| 谁主动 | Nav Sylph 服务来连这台机器 | 这台机器把指标送上去 |
| 目标机要开端口 | **要**（默认 4195） | **不要，一个都不开** |
| 传输 | **HTTPS（强制）** | 取决于本服务自己的 TLS |
| 目标机的网络要求 | 能被服务访问到（同局域网或公网可达） | 能访问服务即可 |

在后台添加服务器时选的是「**这台机器能被本服务直接连到吗**」：选「能」走拉取，
选「不能」走推送。这一问比「局域网 / 公网」更贴近实际——后者要用户自己推导。

判断方法：后台每台拉取模式的机器都有一个「检测」按钮，点一下会真的去连一次。
它能区分「连不上」（路不通）和「连得上但没装 agent」（主机活着，端口没人听）。

**推送模式一个端口都不开**——这是它相对拉取最大的安全收益：内网机器上不会多出
一个只靠 token 保护的网络服务。

## 安装（一行命令）

在后台点这台机器的「部署」，把生成的那一行复制到**目标机**的终端执行：

```bash
curl -fsSL https://nav.example.com/agent/install.sh | sudo bash -s -- \
  --server https://nav.example.com \
  --enroll <一次性令牌>
```

这一行会做完这些事：

1. 探测架构（amd64 / arm64 / armv7）
2. 下载对应的二进制到 `/usr/local/bin/nav-agent`
3. **注册**：agent 自己生成一对密钥与自签证书，把证书交给本服务，换回长期凭据
4. 写 systemd unit 与 `/etc/nav-agent/env`（权限 0600），并启动

令牌是**一次性**的，15 分钟过期，用完即废，且只出现在这条命令里——不会被写进
目标机的任何持久配置。

装完回到后台点「检测」，这台机器会变成「已就绪」，首页也能读到它的指标了。

### 卸载

```bash
sudo systemctl disable --now nav-agent
sudo rm -f /usr/local/bin/nav-agent /etc/systemd/system/nav-agent.service
sudo rm -rf /etc/nav-agent
```

## 升级

重跑一遍安装命令即可（后台点「部署」会生成一条新的）。令牌要重新生成——
旧的那个用过了。

## 参数

### 通用

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--server <地址>` | — | 本服务地址。`enroll` 与 `push` 必填 |
| `--verbose` | 关 | 打印更多诊断信息 |

### `enroll`（注册）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--token <令牌>` | — | 后台生成的一次性令牌。**优先用环境变量 `NAV_AGENT_ENROLL_TOKEN`** |
| `--server-ca <路径>` | — | 本服务证书的 CA（PEM）。**只在自签时需要**，见下 |
| `--mode pull\|push` | pull | 上报方向 |
| `--host <地址>` | 0.0.0.0 | 拉取模式的监听地址 |
| `--port <端口>` | 4195 | 拉取模式的监听端口 |
| `--interval <秒>` | 15 | 推送周期，可选 `10/15/30/60/300` |

**`--server-ca` 什么时候需要。** 绝大多数情况不需要——用 certbot 签的证书本来就在系统根证书池里。
但**自托管用户常用自签证书**，而 Go 的默认客户端只认系统根池：
在 macOS 上它走系统 Keychain、不读 `SSL_CERT_FILE`（那是 Linux 行为），
Linux 上自签证书同样不在根池里，于是 enroll 会握手失败并报：

```
x509: certificate signed by unknown authority
```

这时把本服务的证书路径给它：

```bash
curl -fsSL https://你的服务/agent/install.sh | sudo bash -s -- \
  --server https://你的服务 --enroll <令牌> \
  --server-ca /etc/letsencrypt/live/你的域名/fullchain.pem
```

它被追加进 `RootCAs`（系统根池之上），**不是**跳过证书校验——
`InsecureSkipVerify` 等于把 HTTPS 悄悄降级成明文，本项目不这么做。

### `serve`（拉取模式）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--tls-cert <路径>` | 配置里的 | TLS 证书（PEM）。**必填** |
| `--tls-key <路径>` | 配置里的 | TLS 私钥（PEM）。**必填** |
| `--host <地址>` | 配置里的 | 监听地址。跨机访问必须显式设 `0.0.0.0` |
| `--port <端口>` | 配置里的 | 监听端口 |
| `--insecure-http` | 关 | 逃生门：明文监听。仅限已确认走可信网络的场景 |

配置在 `/etc/nav-agent/config.json`，`serve` 会自动读它，所以 systemd 里不需要
带任何参数。

### `push`（推送模式）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--push-secret <凭据>` | 配置里的 | 推送凭据。**优先用环境变量 `NAV_AGENT_PUSH_SECRET`** |
| `--server-id <id>` | 配置里的 | 目标机在后台的 id。**优先用环境变量 `NAV_AGENT_SERVER_ID`** |
| `--interval <秒>` | 15 | 上报周期 |

推送失败会指数退避，上限 5 分钟——无脑按原周期重试会持续消耗服务端的限流桶，
而那个桶按 IP 计数，一台机器的重试风暴会影响其它所有 agent。

### 环境变量

| 变量 | 用途 |
| --- | --- |
| `NAV_AGENT_ENROLL_TOKEN` | 注册时的一次性令牌 |
| `NAV_AGENT_SERVER` | 本服务地址 |
| `NAV_AGENT_TOKEN` | 拉取模式的 Bearer token |
| `NAV_AGENT_PUSH_SECRET` | 推送模式的凭据 |
| `NAV_AGENT_SERVER_ID` | 推送模式的目标机器 id |

**两个凭据是分开的**，用途不同、互不顶替。填错变量名的表现是推送一直返回
「推送凭据无效」，而日志里不会说你是填错了变量。

### `collect` / `health`

```bash
nav-agent collect   # 打印一份指标 JSON（调试用）
nav-agent health    # 自检：配置、证书、权限、采集、端口
```

`health` 把「为什么连不上」拆成几个能分别回答的问题：配置在不在、证书读不读得到、
私钥权限对不对、采集有没有数据、端口在不在听。单看「失败」没有用——
配置错、证书读不到、端口不通、token 不对，处置完全不同。

## 端点

拉取模式（**只走 HTTPS**：没配证书时 agent 拒绝启动）：

| 路径 | 鉴权 | 说明 |
| --- | --- | --- |
| `GET /health` | 否 | 存活检查，返回 `{"status":"ok","version":1}`。**不含主机名** —— 它不需要鉴权，泄露主机名等于给每个能扫到该端口的人一份资产清单 |
| `GET /metrics` | **是** | 指标 JSON，需要 `Authorization: Bearer <token>`。主机名在这里 |

`/metrics` 返回：

```json
{
  "version": 1,
  "cpu": 0.234,
  "memoryUsed": 5033164800,
  "memoryTotal": 17179869184,
  "memoryPercent": 0.293,
  "load1": 1.82,
  "load5": 1.41,
  "uptime": 691652,
  "cores": 8,
  "hostname": "my-nas",
  "platform": "linux",
  "sampledAt": 1790872081324
}
```

`cpu` 为 `null` 表示两次采样间隔过短、没有可比的差值——**这不是 0%**，别当成
「完全空闲」读。macOS 上恒为 `null`，见「前置要求」。

> 自检命令要带 `-k`（或 `--cacert`）：目标机用的是自签证书，
> 普通 `curl https://…` 会报证书错误，那是预期的，不是故障。

## 防火墙

只在本机启用了防火墙时才需要（仅拉取模式）：

```bash
# firewalld
sudo firewall-cmd --permanent --add-port=4195/tcp
sudo firewall-cmd --reload

# 或 ufw
sudo ufw allow 4195/tcp
```

## 排错

| 现象 | 检查 |
| --- | --- |
| 启动即退出，提示「拉取模式需要 TLS 证书」 | 没注册过。先跑 `nav-agent enroll` |
| 后台显示「未部署」 | 目标机上没跑安装命令，或跑到了别的机器上 |
| 后台显示「等待部署」 | agent 在跑，但它还没向本服务注册。重跑一次安装命令 |
| 后台显示「证书异常」 | 证书与注册时不一致。**如果你重新装过 agent，重新注册即可；否则可能是中间人，先查网络** |
| 后台显示「离线」 | 路不通。检查地址、端口与网络 |
| 显示「凭据被拒」 | 重新部署一次即可换新 token |
| 显示「端口被占用」 | 目标机该端口被别的程序占用了，改一下 agent 的端口 |
| CPU 一直是 `—` | Linux 上极少发生；若持续如此请提 issue 并附平台信息。macOS 上是预期行为 |
| 内存占用偏高（macOS） | 正常。macOS 把内存拿去做文件缓存，本 agent 已用 `vm_stat` 排除可回收缓存，读数与「活动监视器」一致 |

最快的排查方式：先在目标机上跑 `nav-agent health`，再在后台点「检测」。

## 凭据放在哪

| 文件 | 内容 | 权限 |
| --- | --- | --- |
| `/etc/nav-agent/config.json` | 服务端地址、证书路径、token / 推送凭据 | 600 |
| `/etc/nav-agent/env` | 同上的环境变量形式，供 systemd 读取 | 600 |
| `/etc/nav-agent/cert.pem` | 自签证书 | 644 |
| `/etc/nav-agent/key.pem` | 私钥 | **600** |

**凭据不写进 systemd unit。** unit 文件会被 `systemctl cat` / `show` / `status`
打印出来，也常被用户贴进 issue——所以走 `EnvironmentFile`。

## 安全

### token 泄露意味着什么

**拿到 agent token ≈ 拿到那台机器的实时只读监控数据。** 具体是：CPU 与内存占用、
系统负载、运行时长、主机名（`/metrics` 里返回）。

**不能**通过 agent 执行命令、改配置、读文件或访问内网其它主机 —— agent 只读
系统计数器，只回 JSON。

真正要防的是信息泄露与被当作跳板：

1. **内网信息泄露。** 监控目标通常是 NAS、软路由、家用机，这些恰好常在局域网。
   token 一旦泄露且那台机器可达，攻击者就知道你家有哪些机器、叫什么、什么时候开着。
2. **公开暴露的 agent。** 若某台 agent 设了 `--host 0.0.0.0` 而防火墙又没关，
   那它就是一个公开的「你的机器都在这里」的信息源。
3. **横向移动的跳板。** 主机名 + 内网角色信息（NAS、路由器）会帮攻击者判断下一步打哪台。

**token 是明文等价的凭据**：它在命令行与环境变量里都是明文，`ps` 输出与 shell
历史都看得到。所以：

- 优先用**环境变量** `NAV_AGENT_TOKEN` 而非 `--token`
- 目标机上的 token 用**每台不同**的值，别所有机器共用一个 —— 共用时泄一台等于泄全部
- agent 只在你信任的网络里用 `--host 0.0.0.0`；能走 VPN 或 SSH 隧道就别直接暴露端口

### 传输为什么必须是 HTTPS

token 能读到 CPU、内存、系统负载与主机名。**走明文 HTTP 等于把这个凭据公开在
网络上** —— 同一网段里的任何人抓一次包就拿到了。所以 agent 在拉取模式下**没有
证书就拒绝启动**，不提供「默认明文」这个选项。

信任建立靠**注册时的一次性令牌**：后台生成它、目标机用它把证书交上来，信任随之
建立。令牌 15 分钟过期、只能用一次、重复签发即作废旧令牌，且只存在于那条
部署命令里。

注册之后这台机器的证书就被记住了。**如果它后来变了**（你重新装了 agent，
或有人在中间替换），后台会显示「证书异常」：

- 是你自己重新装的 → 在后台重新部署一次
- 不是 → **有人在中间**，先查网络

### 泄露后怎么办

在后台点该服务器的「部署」，重新部署一次即可——那会换一枚新令牌、注册出新的
证书，旧 token 随即失效。

推送模式的凭据同理：重新部署会换一枚新的推送凭据，**旧的立即失效**，所以要同步
更新目标机上的 `NAV_AGENT_PUSH_SECRET` 再重启，否则会开始报「推送凭据无效」。

> 重新部署**不需要**改 Nav Sylph 的管理密码。三者独立。

### 推送凭据泄露意味着什么

**拿到推送凭据 ≈ 能伪造那台机器的监控数据。** 具体是：能往 Nav Sylph 写任意指标
（会被显示在所有人的首页上），但**不能**读到其它机器、不能改配置、不能执行命令。

推送凭据与 agent token 是**两回事**：

| | agent token（拉取） | 推送凭据（推送） |
| --- | --- | --- |
| 方向 | 服务来问 | 机器去报 |
| 泄露后果 | 读到那台机器的实时指标 | 能**伪造**那台机器的指标 |
| 存在哪 | 配置里的密文 | 配置里的哈希（明文只在注册时出现一次） |
| 怎么换 | 重新部署一次 | 重新部署一次（旧的立即失效） |

**推送凭据泄露比 token 泄露轻**：token 是「读到真实数据」，凭据是「写入假数据」——
后者不泄露信息，但会误导监控。两种凭据都要每台不同。

### 已有防护

- token 可从环境变量或 `--token` 读（环境变量更安全：命令行会出现在 `ps` 输出里），
  但**为了重启后仍能鉴权，它必须落盘**：写在 `/etc/nav-agent/config.json`
  与 `/etc/nav-agent/env` 两处，两份都是 `0600` 且属主是 root。
  **不**写进 systemd unit —— unit 会被 `systemctl cat` / `show` / `status` 打印出来，
  也常被用户贴进 issue。所以机器上拿到 root 的人可以读到 token，
  这与 agent 本来就要读的 `/proc/meminfo` 是同一层信任。
- `/metrics` 需要鉴权；未授权返回 `{"error":"unauthorized"}` —— 不提示 token 的长度或前缀，避免帮攻击者缩小猜测空间
- token 比较用定长比较（`crypto/subtle.ConstantTimeCompare`）
- **`/health` 默认不返回主机名**。它不需要鉴权，所以只回 `{"status":"ok","version":1}`；
  主机名只出现在需要鉴权的 `/metrics` 里
- agent 只读 `/proc`，不写任何文件
- **推送模式默认不监听任何端口**，内网机器上不会多出一个网络服务
- 推送载荷在落库前被压到已知形状：越界的数值回落为安全值（`cpu` 越界变 `—`），
  超长字符串被截断，超过 4KB 的载荷整个拒收
- 推送端点有独立的限流桶（120 次/分钟），不会消耗管理端或匿名读接口的配额

## 指标口径

- **CPU** —— 两次采样（间隔 200ms）的累计时间差分。`/proc/stat` 给的是自开机以来的
  累计值，单次读没有百分比
- **内存** —— `已用 = 总内存 − 可用`。Linux 的可用取 `MemAvailable`；macOS 的可用取
  `free + inactive + speculative + purgeable`（`inactive` 是可回收的文件缓存，
  算作可用才是用户视角）
- **负载** —— 读 `/proc/loadavg`

## 协议版本

`/metrics` 返回里的 `version` 必须与服务端一致，不一致时 Nav Sylph 会明确报错而不是
把不认识的字段当 0 读进去。当前 `VERSION = 1`。

**换成 Go agent 不构成协议版本变更**：上报的指标载荷字段一个没动，TLS 是通道层的事。
看到这里若以为漏升版本，那是没升。

升级服务端后，如果目标机上的 agent 还是旧版，卡片会显示「agent 协议版本 X 与
服务端 Y 不一致」——重新部署一次即可。
