## 逐条验收

### 1. 停止在 IndexedDB 事务递增代次并删除本地口令、派生凭据和待上传任务，跨标签页取消调度，保留本地导航

- 实现：`clearSyncConnection()` 是**唯一的**断开路径（停止、删除、服务端判终态都走它），在**一次** `writeSync` 里递增连接代次并清 `connection`/`pending`/`claim`/`uploadedPayloadKey`；本地导航（不在这个存储里）与「替换前的副本」`recovery` 不动。`stopSyncLocal()` 随后广播 `stopped`，再**尽力**撤销本设备令牌。
- 真实浏览器（两个真标签页，同 profile 共享 IndexedDB）：t1 点「停止同步」→「确认停止同步」后 —— t1 `conn:false`、`epochMem 1→2`、`epochRec 2`（内存与记录一致）、`syncPollTimer:null`、提示「已停止同步，本机导航保持不变」，本机导航 **3 个分类 / 9 个书签**不变；**t2 未刷新**即 `conn:false`、`poll:false`、页脚回到「同步」；t1 刷新后仍是未连接。
- 用例：`tests/sync-engine.test.js`「停止同步：一次事务递增连接代次并清掉凭据与待上传…」（先让定时器真的活着再停：断言 `intervals()===0` 与 `pending()===0`，并断言修订号**只走一格**）、`sync-client.test.js`「停止同步：清凭据与递增代次在**同一次**落盘里…」（事务内同时含 `connEpoch+1` 与 `connection:null`，`doesNotMatch(recovery:)`）。
- 变异：① 代次 +1 挪出那次事务；② 把 `recovery` 一起清掉；③ 不停定时器 —— 各自被对应用例检出（21 条变异全红，见文末）。

### 2. 所有连接落盘和任务入队均事务比较代次，迟到响应及排队写入不能恢复凭据；离线断开允许完成，在线尽力撤销令牌

- 实现：`local-navigation.js` 的 `writeSync(patch, revision, expectedEpoch)` 在**写事务内**比较记录里的 `connEpoch`（不符抛 `code:'epoch'`）；`persistSyncRecord()` **一律**带当前代次，只有「推进代次的那条路」（停止/删除/连接成功）用 `writeSyncWithEpochRetry()`。
- 真实浏览器（真实 IndexedDB）：① 模拟「另一个标签页刚停止」（记录代次+1、修订号也+1、内存不动）→ 迟到落盘被拒 `code=conflict`，记录里 `connection` 仍为空；② 把内存修订号对齐后再落盘 → 被拒 **`code=epoch`**（这正是新守卫自己的契约），记录仍无连接、代次没被倒回去。
- 离线：`sync-engine.test.js`「离线停止：撤销请求不发，但本地断开照样完成」；在线时停止恰好发 1 次 `POST /api/sync/device/revoke`（用例断言 1 条；真实浏览器运行的服务器日志里该请求出现 1 次）。
- 用例：`sync-engine.test.js`「别的标签页停止后，本标签页迟到的落盘被拒，凭据不会被写回」「另一个标签页刚停止时，本标签页的连接不会被写回去（连接落盘也被拦）」——后者钉的是**连接**落盘（迟到连接请求不能把凭据写回）。
- 变异：① 关掉 `local-navigation` 的比较；② 关掉**引擎夹具**的比较（夹具自检：证明上一条红确实是这条守卫造成的，而不是夹具漏建模）；③ 连接时只在内存里 +1、不落盘（见下「自查发现」）。三条各自变红。

### 3. 云端删除在线重新验证口令并明确确认，暂停上传，事务删除配置和撤销全部设备；失败保留连接，结果不确定先核对原代次

- 实现：`POST /api/sync/space/delete` 是**双要素**（`Bearer` 设备令牌钉住空间 + body 里的口令证明再验一次），单事务完成「标记删除 + 清内容 + 释放口令槽 + 吊销该空间全部设备 + 删空间作用域回执」；客户端 `requestDeleteSpace()` 离线直接拒绝，`confirmDeleteSpace()` 期间置 `syncDeleting` 挡掉一切上传（排程处与发请求处两层），网络错/5xx **再试一次**，第二次的 410 就是核对答案。
- 真实浏览器：口令输错 → 对话框显示「**口令不正确，未删除任何内容**」、连接保持、`/api/sync/space/check` 仍 `exists:true`；口令正确 → 断开、`epoch 4→5`、提示「云端空间已删除，本机导航已保留」、导航不变、`exists:false`、第二台设备令牌 **410 `space_deleted`**、**再删一次也是 410**（即客户端重试所依赖的那个确定答案）。
- 用例：`sync-http.test.js`「删除云端空间——双要素鉴权、墓碑、吊销全部设备、清空间回执」（含口令错 403 后空间原样、两台旧设备都 410、重试 410、管理员会话与邀请码接口不受影响）；`sync-engine.test.js`「删除期间暂停上传」「删除/停用开始时已经排好的那一轮，到期也不许发出去」「口令不正确就保留连接，什么都不删」「第一次网络不确定，第二次拿到「已删除」就按删除收尾（不重建）」。
- 边界（诚实说明）：**「响应真的丢掉」只做到引擎层**（注入网络错 + 服务端真实的 410 答案），浏览器里没有真的丢弃过一次响应。

### 4. 删除与上传竞争串行，旧设备保留本地并断开，不自动重建；同口令新建采用新代次和新令牌

- 服务端：删除与写都在同一个库上单事务执行，谁先到谁生效。
- 用例：`sync-http.test.js`「删除与上传竞争——删除先完成时旧上传失败，且不会让空间复活」（真并发 `Promise.all`：删除 200、写只能 200 或 410；最终空间 `deleted=1`、内容 `{}`、**全库只有一个空间行**）；「同口令重建用新 id 与新代次，旧令牌够不到新空间」；「同一个口令反复「建 → 删 → 再建 → 再删」都成立」。
- 真实浏览器：删除后用**同一口令 + 新邀请码**重建 → 新空间 id（`7c4733bc` ≠ 删掉的 `86f3096b`）、`generation` 由 1 变 **2**（墓碑代次 +1）、旧设备令牌仍 **410**；整个运行期间服务端日志里 `POST /api/sync/space/create` **恰好 2 次**（就是用户手动创建的两次）——没有任何路径会「因为删掉了就自动重建」。
- 旧设备保留本地并断开：`sync-engine.test.js`「空间已被删除：读路径判为终态 → 本地断开、保留本地导航、文案说清是删除」（断言 `recovery` 留下、提示点名「已被删除」而不是笼统的「连接已失效」）。
- 变异：① 删除不校验口令；② 不吊销设备；③ 不清空间回执；④ 真删空间行（墓碑消失 → `space_deleted` 不可达）；⑤ 先判吊销后判删除（墓碑读不到）；⑥ 重建不取「旧代次+1」；⑦ 墓碑唯一性取口令而不是空间 id；⑧ 删除失败后自动重建 —— 各自变红。

### 5. 停止不影响其他设备，删除不影响管理员配置或会话；重新连接按首次方向选择

- 停止只吊销**本设备**那一行：`sync-http.test.js`「停止同步撤销本设备令牌——只影响本设备，幂等，坏令牌也返回成功」（同一空间另一台设备仍 200；断言库里只 1 行被吊销）；真实浏览器里用 curl 造的第二台设备在 t1 停止后仍 **200**。
- 删除只动 `sync_*` 四张表：同一条 HTTP 用例断言删除后 `/api/session` 与 `/api/admin/sync-invites` 仍 200（管理员配置在 JSON、会话在 SQLite 的会话表，不在空间表里）。
- 重新连接：真实浏览器阶段 6 → `exists` 态给出「使用云端配置 / 以本机配置替换云端」两个方向（首次方向选择），选「以本机配置替换云端」后回到已连接、`epochMem==epochRec==4`。

### 6. 真实 HTTP 与多浏览器测试停止刷新、延迟写入、删除响应丢失、旧设备重上线及同口令重建

| 场景 | 证据 |
| --- | --- |
| 停止后刷新 | 真实浏览器：t1 刷新后仍未连接；t2 不刷新即取消调度（`poll:false`） |
| 延迟写入 | 真实浏览器两种拒绝码（`conflict` / `epoch`）+ 引擎用例两条 |
| 删除响应丢失 | 引擎用例（网络错重试 → 410 收尾）+ 真实 HTTP 的「第二次删除 = 410」（浏览器里没有真的丢包，见 §3 的边界） |
| 旧设备重上线 | 真实 HTTP：旧令牌 410 `space_deleted`；引擎：读路径判终态 → 断开并保留本地 |
| 同口令重建 | 真实浏览器（新 id、代次 +1、旧令牌 410）+ 真实 HTTP 的往返删除用例 |

- **两个真标签页**（同 profile 共享 IndexedDB）这一条同时补上了 #8 留下的空白。
- 补验（审查修完之后，真实浏览器 + 直接改副本库的 `sync_spaces.disabled`，因为停用的界面入口归 #10）：停用 → 工具栏「立即同步」→ 对话框进入**停用态**（「空间已被停用 / 管理员重新启用后点「重试同步」…重新输入口令没有用」）、连接保留、`poll=false`、期间的真实 `saveLocalNavigation` 改动**一次都没发**（服务端 POST 计数不变）→ 管理员恢复 → 点「重试同步」→ `halted=false`、`poll=true`、状态回到「已同步」，且**停用期间那次改动补传成功**（POST 计数 3 → 4）。
  - 这一次补验本身也踩了一次自家坑：第一次跑没清 Service Worker/caches，浏览器执行的是缓存里的**旧 bundle**，而旧代码把 403 当凭据失效直接断开了连接，于是量到的是旧行为。清缓存重跑后才是上面的数。
- 全量回归：`node --test tests/*.test.js` = **738 / 738**（基线 `ce45379` 实测 **705**；本轮 +33：HTTP +5、引擎 +20、接线 +8）。
- 变异：**30 / 30 条按预期变红**，且每条都逐字节还原（`cmp` 校验过四个源文件与变异前一致）。
  - 三条最初没变红的，逐条查清了原因，都不是「守卫够用」而是**我的守卫/变异写错了**：① 变异期望的用例名指错（断言在另一条用例里）；② 我加了**两条**恢复路径（认领时读回代次 + `epoch` 走重读），拆一条另一条仍守得住——那是冗余不是缺陷，所以把两条**一起拆**才该变红；③ 「删除失败后补排上传」的断言用了 `clock.pending()`，它把轮询的 interval 也算进去，于是「只接回轮询、没补排上传」照样通过——改成指名 `syncDebounceTimer`/`syncMaxWaitTimer`。

## 自查发现并修掉的两个缺陷（都由本轮验证抓到，未进入任何发布版本）

1. **连接成功时只在内存里递增连接代次、没有落盘**（`finishSyncConnection`）。症状：连接明明建好了，紧接着的上传/指纹落盘全被事务拒掉 → **刚连上就显示「同步失败」**，而对话框还会把它报成「创建失败」。真实浏览器第一次跑就撞上（`epochMem:1 / epochRec:0`）。修法：代次的递增与写入连接放进**同一次**落盘，并补两条用例（正常连接之后还能落盘；别的标签页停止时代次 CAS 拦住连接落盘）+ 一条变异。
2. **墓碑的唯一性来自口令哈希而不是空间 id**。症状：同一个口令「建→删→再建→再删」的第二步，删除接口 **500 `UNIQUE constraint failed: sync_spaces.proof_id`**。修法：墓碑的 `proof_id` 用 `'gone:' + 空间 id`，原口令哈希挪进独立列 `deleted_proof_id`（重建时按它取代次最高的 +1），并补一条往返删除用例 + 一条变异。

3. **「空间被停用」落到了「口令 + 再输一次」的表单上**。停用原来复用了 `setSyncState('error')`，而对话框对 `error` 态走的是首连表单——用户看到的是「请重新输入口令」，可这里重新输口令**没有用**（凭据仍然有效，只是空间被停用）。真实浏览器补验看到的就是这一屏。修法：给停用一个自己的对话框状态（`halted`：说清状态、明说「重新输入口令没有用」、给「重试同步 / 停止同步 / 关闭」三个出口）+ 接线守卫 + 变异。

### 审查（两轴，针对未提交工作树）与补验

两轴并行（规范轴对照仓库文档与既有踩坑清单；规格轴逐条对照 issue #9 的验收原文与计划的「不在本次范围」）。修掉的：

| 来源 | 问题 | 修法 |
| --- | --- | --- |
| 两轴一致 | **停用没有解除路径**：`syncHalted` 只置位不复位，管理员恢复后点「立即同步」也上传不了（计划 Q3 逐字承诺过这条）。 | 读成功即解除（`syncPullCheck` 成功分支），并把停用期间一次都没排过的改动按指纹补排；补用例 + 变异 |
| 规范轴 | **代次可能回退**：`writeSyncWithEpochRetry` 的代次 `+1` 在循环**外**求值，重读重试时会把更低的旧值写回去。 | 改成 `{ bumpEpoch: true }`，在重试循环**内**重算；接线守卫钉住这一句 + 变异 |
| 规范轴 | **断开落盘失败会抛出去**：`clearSyncConnection` 的 4 个调用点都没有 catch（旧实现从不 reject），漏掉的会变成未处理的 rejection，而界面已经显示未连接。 | 在该函数内部收口并明确提示「本机断开未保存…」；补用例（不许 throw + 不许动内存代次）+ 变异 |
| 规范轴 | **被拒的 `epoch` 没有恢复路径**：认领时只读回修订号、不读代次，落盘必被拒，上传卡在「失败 + 无限退避」，而恢复实际上依赖 BroadcastChannel 送达（架构文档明说不依赖它）。 | 认领时把代次读回内存 + 上传失败遇到 `epoch` 走「重读再排一轮」；两条一起拆的变异证红 |
| 规范轴 | **删除失败只接回轮询、没补排那一轮上传**，页脚却写「同步中」。 | 失败分支按指纹补排；断言指名上传定时器 |
| 规范轴 | 删除路径遇到 `space_disabled` 说了「已暂停」却没落地挡板。 | 走同一个 `applySyncHalt`（说到做到），补断言 |
| 规范轴 | 死代码：`disconnect` 字段没人读、`stopSyncLocal(options)` 没人传参、删除响应里的计数没人用。 | `handleSyncTerminal` 显式按 `disconnect` 分支；删掉参数；计数在 HTTP 用例里断言（`revoked === 2`） |
| 规范轴 | 两条恒真断言（`>= 1` 充当唯一性、对已在方法清单里的符号做存在性判断）。 | 删掉，唯一性交给 sync-client 那条守卫 |
| 规范轴 | 竞争用例的断言消息与条件矛盾（允许 200 却说「必须是 410」）。 | 消息改成「两种顺序都允许，终态必须是墓碑 + 空内容」，并另加一段**确定性**的「删除先完成」；管理员侧数据按计划逐项断言（配置与收藏删除前后逐字节一致） |
| 规范轴 | 两份既有仿真样例仍写「停止同步与删除云端空间在后续版本提供」。 | 两处改掉，并新增 `docs/mockup-sync-stop-delete.html` |
| 规范轴 | 架构文档新增的「`syncTerminalOf()` 是唯一映射处」与事实不符（服务端各有一句同义文案，且已经在两处漂移）。 | 改成如实表述：它是「错误码 → 用户下一步」的**唯一分类处**；服务端那几句是 API 的错误信息，终态路径上界面只显示分类结果（删除的**非终态**失败才会显示服务端原话） |

**审查里不成立、已写进记录不再重复调查的**（规范轴自己列的排除项）：`checkSync` 会把代次冲成 0、夹具比真货宽松、墓碑与既有 schema 冲突、删除后不撤销令牌、终态断开清掉 `recovery`、挡板挡不住已排好的那一轮、只读连接读服务端库不稳——逐条核对后都不成立。

**审查指出的、我评估后不做的**：① 「`syncHalted` 是否该落盘」——不落盘意味着刷新即解除，这是当前的有意行为（刷新是用户的明确动作，且 #10 会引入策略轮询），保持不落盘；② store 层单测（`revokeDevice`/`deleteSpace` 只有真实 HTTP 覆盖）——按 AGENTS.md 第 4 条「改哪个模块跑哪个定向测试」，HTTP 层是真实服务 + 真实库，满足要求。
