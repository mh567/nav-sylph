# Sylph 导航页轻量交互调研

日期：2026-09-26
范围：个人导航页中的搜索、点击、对话框和书签操作。本文只做资料调研和可行性判断，不实施代码修改。

## 摘要

Sylph 适合采用低幅度、短时、紧贴操作结果的反馈：输入后及时呈现搜索结果，点击后给出清楚的选中或按下状态，管理操作完成后用轻量状态提示，弹层开合保持一致。微动效用来补充状态变化，不应延迟高频操作或承担唯一的信息传递。

推荐优先级：

1. 保持搜索结果更新顺畅，避免每次输入都做不必要的大块 DOM 工作。50 ms 防抖本身很短，体验风险更可能出在结果节点反复重建的计算、布局和焦点连续性上。
2. 保留卡片已有的 hover/按下反馈，检查键盘焦点也能看出当前目标。避免持续脉冲、弹跳、明显缩放或把操作锁在动画完成之后。
3. 统一对话框开合节奏，采用短促淡入淡出或很小的位移即可。普通状态和结果文案必须在动效之外可读。
4. 对频繁出现的搜索、选择、点击反馈尽量轻量。对保存、复制、删除等操作，在成功或失败确认后给出明确状态；异步操作应等真实结果后再报成功。
5. 尊重 `prefers-reduced-motion: reduce`，去掉非必要位移、缩放和连续动画，保留即时状态变化与内容可见性。

## 本项目边界

主任务提供的代码盘点显示：搜索使用 50 ms 防抖，结果更新时每次通过 `innerHTML` 重建；书签卡片已有 hover 上移和 active 下压；部分 modal 入场动画在 200 至 300 ms，收藏编辑弹层开合节奏未统一；CSS 暂无 `prefers-reduced-motion`；页面多处使用原生 `prompt`、`confirm`、`alert`。

这些事实意味着轻量交互的第一阶段更适合围绕状态及时性、一致性和可访问性收敛。50 ms 防抖不会单独证明体验一定快或慢。结果重建在收藏量大、DOM 较重或主线程繁忙时可能增加呈现延迟，需用实际交互性能数据确认。当前对原生对话框的使用也不意味着需要全部替换；可先识别高频或打断流程的场景，再评估统一的应用内反馈。

## 按操作场景的可行方案

以下是基于现有代码与下述规范提出的设计假设，具体幅度和时长需要交互原型验证。

1. **输入与浏览搜索结果**：输入框获得焦点时保持稳定的边框反馈；建议列表快速更新，当前键盘选中项始终清楚可见。每次按键不叠加卡片进场动画，也不让旧结果突然闪空。若真实设备上出现卡顿，先测量索引计算和结果重建耗时。
2. **提交搜索与打开结果**：按下按钮或回车时立即给出简短按压状态，随后按原有导航行为打开目标。反馈不推迟新标签页的打开；页面也不把“点击了”表述成“目标网站已加载完成”。
3. **点击首页书签**：沿用现有 hover、按下与键盘焦点，统一幅度和释放节奏。用户应在指针按下时感到卡片有响应；外部页面的加载结果仍由浏览器呈现。
4. **打开与关闭对话框**：统一遮罩、弹层与关闭动作的节奏。焦点进入对话框，关闭后回到触发按钮；键盘关闭与点击取消产生一致结果。高频普通提示优先使用页面内文字状态，删除或放弃修改等操作保留明确确认。
5. **保存、复制与删除**：先显示操作进行中，再根据真实成功或失败显示结果。失败时保留输入和可重试路径；完成提示短暂、安静，不抢走焦点。复制链接的提示还应以剪贴板 API 的实际结果为准。
6. **声音与设备震动**：暂不列入基础方案。先验证视觉和文字反馈能否达到目标，再按设备支持、使用场景和用户偏好评估可选触觉反馈。搜索和书签点击属于高频操作，默认加入声音容易造成重复打扰，这是产品判断，仍需用户研究验证。

## 借鉴锤子网站的前台设计方案

### 参考范围与设计定位

2026 年 9 月查看的[锤子商城官方首页](https://www.smartisan.com/)呈现了深色顶栏、清晰的二级导航、留白明确的商品分组，以及以产品名称配一句简短价值说明的卡片。首页首屏使用高饱和度、大面积的商品活动图。这一观察只代表当前可访问页面，页面页脚带有 2020 年版权标记，不据此推断品牌目前的设计策略。[Red Dot 的 Smartisan OS 项目说明](https://www.red-dot.org/project/smartisan-os-13350)提到界面、动画、中文排版与功能细节，但对象是操作系统，不能当成网站交互规范。

Sylph 的设计定位：让搜索与常用书签成为首屏最清楚的两个入口，用精确排版、安静的层次和可触知的按压反馈，形成类似精心打磨过的工具感。借鉴的是秩序、细节和语言节奏，不复制品牌标识、商品图片、宣传口号或商城首页的活动视觉。

### 可以转化的设计语言

| 观察与原则 | Sylph 的转化 | 边界 |
| --- | --- | --- |
| 导航与内容分层清楚 | 搜索区保持视觉中心，分类标题、卡片、辅助操作依次降低视觉权重 | 不增设商城式双层导航，避免挤占导航页首屏 |
| 标题短，副文案只解释当前价值 | 搜索模式、空结果、保存结果使用简短中文状态文案 | 不在每次点击后加入口号或俏皮话 |
| 卡片有整齐的节奏和可触知的质感 | 在纯文字卡片上用顶缘高光、柔和阴影和压下反馈形成轻拟物手感 | 控制单卡尺寸与装饰密度，维持导航效率 |
| 主视觉有明确焦点 | 用一处有限的强调色标识当前搜索模式、选中项与主要动作 | 不把高饱和度商品横幅移植到首页 |
| 细节围绕操作结果 | 同一套状态语法覆盖待命、按下、进行中、成功、失败 | 视觉反馈不能假称外部网站已加载或服务器已保存 |

当前 CSS 已有浅色与深色变量、搜索聚焦阴影、书签 hover 上移、active 下压和键盘焦点描边。设计实施应先统一这些现有规则的幅度、状态和语义，再决定是否增加装饰。搜索和卡片目前均使用通用的 `200ms` 过渡，多个组件写有 `transition: all`；若原型出现拖沓或不必要的属性动画，可按组件改为仅过渡颜色、阴影和小幅位移。这里是代码审阅得出的实施方向，尚无浏览器耗时证据。

### 前台场景稿

1. **搜索待命与输入**：保留大搜索框，输入获得焦点后以边框和轻微阴影表达“已准备好”。搜索引擎与收藏检索模式用稳定的文字标签区分。输入期间结果位置保持稳定，当前键盘选中项使用清楚的底色或侧边标记。每个字符输入后不触发整排卡片动画。
2. **搜索结果与空状态**：结果项沿用书签卡片的文字与间距规则，不显示图标。无结果文案建议为“没有找到相关收藏，换个词试试”，附一个可执行的返回或清空入口。外部搜索与站内收藏检索要明确标注目的地。
3. **书签卡片**：保留接近原版的紧凑尺寸和分类网格，只显示名称。静止时用边缘高光与细腻阴影表达可按压；鼠标悬停时让高光跟随指针产生微小变化，同时略微抬升，按下时快速压回。键盘聚焦有同等明确的轮廓。触屏使用按压状态，不依赖 hover。打开新标签页后不显示“已打开成功”，因为 Sylph 无法确认目标站点完成加载。
4. **分类与页面层次**：分类标题保持低于书签标题的对比度，用间距和细线组织内容。常用入口优先靠近首屏，管理和帮助入口保持可见但降低视觉权重。书签较多时优先解决扫描速度，避免用卡片逐一入场动画制造等待。
5. **对话框与保存**：打开时遮罩和面板采用一致、短促的过渡；标题说明正在处理什么，主要按钮写具体动作，例如“保存修改”。提交后按钮显示进行中，收到服务器响应后显示“已保存”或明确失败原因。关闭前未保存的内容仍由确认步骤保护，焦点进入和返回应可预期。
6. **微文案**：语气平实、具体、短句。建议候选包括“搜索网页或收藏”“正在保存”“已保存到服务器”“保存失败，请重试”“链接已复制”。这些是 Sylph 原创候选文案，需按实际功能和结果核对后使用。“已保存到服务器”只用于后端确认成功的操作，浏览器本地状态不能套用。

### 交互节奏与验证方式

当前原型把浅色、深色和三条交互流程放在同一个紧凑导航页中。卡片悬停以高光、阴影和小幅抬升共同表达材质，按下立即压回；搜索结果与弹层保持阅读优先。动效幅度与时长仍是可调参数，不预设唯一正确值；遵守减少动态效果设置。完成视觉评估后，用日常书签数量分别观察桌面和手机，核对键盘操作、触屏按压、焦点返回、错误提示与真实响应速度。

采纳条件：用户一眼看出当前搜索模式与可点击目标；按下有即时回应；保存状态与服务器结果一致；连续搜索不会因动画分散注意力；深色主题和减少动态效果设置下仍能清楚区分状态。若原型只提高新鲜感，却拉长搜索或书签操作，应缩减效果。

### 原型供评估

第一版的三个结构候选被用户否定，主要问题是入口过大、偏拟物细节不足、悬停质感平淡。第二轮又收到焦点蓝框突兀、希望纯文字入口、配色需要更护眼的反馈。独立试验稿 [`prototype-sylph-interactions.html`](prototype-sylph-interactions.html) 已收敛为紧凑的纯文字版：保留原首页的搜索与分类书签结构，通过卡片边缘高光、柔和阴影和指针位置反馈表达轻拟物质感，在搜索框、结果浮层和底部操作区使用透明材质。页面以暖灰背景、深棕文字和少量陶土色强调建立舒适的阅读环境，色彩方向参考 [Anthropic 官方首页](https://www.anthropic.com/) 的暖色中性基调，具体色值为 Sylph 原型自定。搜索输入框点击时只让整个搜索容器产生柔和边缘反馈，按钮保留暖色键盘焦点标记。可切换浅色与深色，尝试输入关键词、用 `/` 切换收藏检索、按方向键选择结果、悬停或按下书签、打开管理示例并模拟保存失败。原型使用内存中的样例数据，所有保存与跳转反馈均明确标注为模拟，不调用服务器。此文件位于 `docs`，不属于实际首页的发布资源。

第三轮反馈指出浅色悬停光感偏弱、管理按钮和搜索框缺乏精致感，同时发现搜索模式占用了原本的搜索引擎入口。当前原型将“网页/收藏”模式按钮与搜索引擎按钮并列；网页模式可从菜单选择 Google、Bing、DuckDuckGo，收藏模式暂时收起引擎按钮，返回网页模式后保留选择。引擎切换只改变原型状态和提交提示，不发起外部搜索。搜索框与按钮上的暖色光晕跟随鼠标位置，浅色主题提高了光晕与表面的明度差；管理弹层采用中性色取消按钮、低权重模拟失败入口和实色主要按钮。

透明材质的分布参考 [Apple Human Interface Guidelines 的 Materials 章节](https://developer.apple.com/design/human-interface-guidelines/materials)：Liquid Glass 主要用于控件与导航层，内容层保持清晰，并控制使用量。Apple 的原生实现具有系统级实时渲染和环境适配；本网页原型只使用 CSS 模糊、透光、边缘高光与阴影近似表达，并提供不支持模糊或减少透明时的实色回退。两种材质融合的具体视觉效果属于设计实验，需要用户在真实浏览器中评价。

### 原型交互状态核对

| 对象 | 悬停 | 按下或聚焦 | 操作结果 |
| --- | --- | --- | --- |
| 搜索框整体 | 边缘与表面轻微提亮 | 输入聚焦后呈浅内凹，深色主题的凹陷更明显 | 输入本身不弹提示，提交后才反馈 |
| 左侧模式按钮 | 微抬、边缘变暖、阴影增强 | 按下瞬时凹陷，收藏模式持续显示选中状态 | 标签与无障碍状态同步改变，并提示当前模式 |
| 搜索引擎按钮 | 指针位置光晕与细边缘反馈 | 按下打开引擎菜单，选中项在菜单中标明 | 仅网页模式显示；选择保留到下次切回网页模式 |
| 右侧搜索按钮 | 微抬、明暗层次增强 | 按下瞬时凹陷 | 网页搜索只显示原型提交提示，收藏模式打开匹配项或提示无结果 |
| 书签和搜索结果 | 书签高光随指针变化，结果行显示暖色选中层 | 按下凹陷，键盘焦点可辨认 | 仅显示原型点击提示，不声称外部网站已加载 |
| 主题、底部操作和对话框按钮 | 各有悬停提亮或轻微抬升 | 按下凹陷；保存中禁用重复提交 | 主题切换更新按钮文字；保存失败保留输入并取消尚未完成的模拟保存 |

材质语义按操作状态统一：可操作的默认态略微凸起，悬停提示可接近，按下态压入表面。深色主题通过更深的内阴影增强按下反馈，单纯的深色外观不等同于“已按下”。这一判断来自交互直觉与原型设计，仍需实际用户体验验证。

## 官方资料与结论

### 反馈时延与页面性能

Google web.dev 将 INP 不高于 200 ms 作为良好响应阈值，200 至 500 ms 为需改进，超过 500 ms 为较差，并建议以真实用户页面加载的第 75 百分位分别观察移动与桌面数据。INP 衡量交互从输入延迟、事件回调到下一次呈现的整体响应；它用于性能评估，并未规定每个 toast 或动效的时长。Sylph 可把它作为搜索和关键点击响应的性能目标，再结合主观观感验证。[web.dev：Interaction to Next Paint](https://web.dev/articles/inp)

web.dev 的优化指南建议事件回调尽可能少做工作，先让 UI 更新有机会呈现，再把不紧急工作延后；大量客户端 HTML 解析和 DOM 更新可能拖慢下一帧呈现。由此推断，Sylph 的逐次 `innerHTML` 重建值得关注，但是否造成实际延迟取决于结果数量、DOM 复杂度和设备，不能只凭实现方式下结论。[web.dev：Optimize INP](https://web.dev/articles/optimize-inp)

### 微动效和点击反馈

Apple HIG 建议动效服务于体验，不为装饰而添加；反馈动效应简短、准确，并尽可能允许用户不等动画结束就继续操作。Apple 也提醒，频繁发生的普通界面操作通常不宜叠加额外动效。对 Sylph 来说，轻微颜色、边框或阴影变化通常比每次都移动或放大卡片更适合搜索和导航这类高频流程。[Apple HIG：Motion](https://developer.apple.com/design/human-interface-guidelines/motion)

Apple 的指导没有规定通用的网页动画毫秒数。因此本文不将 200 至 300 ms 等现存时长判为不合规，也不把某个时长伪装成官方硬指标。实际可以通过一致性和不阻塞操作来评估现有弹层节奏。

web.dev 的动画性能指南说明，改变尺寸会触发布局，导致其他元素移动或重新计算；布局或绘制代价较高时，优先考虑只改变 `transform` 或 `opacity`。过度使用 `will-change` 也会浪费资源。该指南较早发布，适合支持这些基本浏览器渲染机制，不能替代现代设备上的性能测量。[web.dev：Animations and performance](https://web.dev/articles/animations-and-performance)

### 减少动态效果

W3C WCAG 2.3.3（AAA）要求允许关闭由交互触发的非必要运动，必要功能或信息本身依赖的运动除外。[W3C：Understanding SC 2.3.3](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions)

W3C 的 C39 技术说明展示了通过 CSS `prefers-reduced-motion` 响应系统设置的方式，并明确技术示例属于建议做法，单独采用该技术并非 WCAG 合规的充分条件。[W3C：Technique C39](https://www.w3.org/WAI/WCAG22/Techniques/css/C39)

MDN 说明该媒体特性检测用户是否启用了减少动态效果偏好；`reduce` 表示用户希望减少或替代非必要运动。浏览器支持广泛。适合对 Sylph 的位移、缩放、滑入等效果提供减弱或静态表现，同时保留颜色、边框、文本等状态反馈。[MDN：`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion)

### 浏览器能力与书签

MDN 的 Bookmarks API 属于 WebExtensions，需在扩展清单声明 `bookmarks` 权限，才能搜索、创建、更新、移动和删除浏览器书签。[MDN：Bookmarks API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/bookmarks) 这意味着普通网页不应假设能直接写入用户浏览器的书签栏。Sylph 当前产品模型是管理自己的收藏数据，并支持浏览器书签导入导出；页面内书签操作的状态反馈应围绕 Sylph 自身数据和服务器保存结果设计。扩展化属于独立产品能力，不能由交互动效解决。

若某个操作需要复制链接，MDN 的 `Clipboard.writeText()` 返回 Promise，浏览器更新剪贴板后 Promise 才完成；该 API 仅在安全上下文可用，并可能因权限限制抛出 `NotAllowedError`。[MDN：Clipboard.writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText) 因此成功提示应在 Promise 成功后显示，同时为拒绝或失败提供可见反馈。Clipboard API 的权限和用户激活约束在浏览器间存在差异。开发环境的 HTTP localhost 是否满足安全上下文，应按浏览器规则实测，不要在提示文案中假定所有环境可复制。[MDN：Clipboard API 安全考虑](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)

MDN 说明 `window.alert()` 会等待用户关闭对话框，模态框会阻止用户访问其余界面，因此不适合作为频繁的普通成功提示。对 Sylph 的 `alert`、`confirm`、`prompt` 应按用途逐个判断，保留需要明确确认的场景，普通完成通知可采用不抢焦点的状态提示。[MDN：Window.alert](https://developer.mozilla.org/en-US/docs/Web/API/Window/alert)

## 建议的验证标准

- 搜索输入期间结果持续可见，键盘焦点和当前选择不会因结果更新意外丢失。
- 关键交互的 INP 在真实数据第 75 百分位达到 200 ms 内；若未达到，先定位事件回调、渲染和主线程任务，不用额外动画掩盖延迟。
- 搜索及常见点击不会触发持续或显眼的运动；动效结束不成为继续操作的前提。
- 设置系统减少动态效果后，非必要位移、缩放和连续运动消失或明显减弱，操作状态仍可辨认。
- 对话框的开合行为、焦点进入与返回、键盘关闭方式和关闭后的内容状态保持一致。该项属于实施验收建议，需另按当前交互结构审查。
- 书签保存、删除及复制反馈跟随实际成功或失败状态；应用内数据与浏览器原生书签的边界表述清楚。

## 限制

本调研使用规范和平台厂商文档建立原则，未对 Sylph 执行浏览器性能测量、无障碍审计或动效用户测试。web.dev 的 INP 阈值用于响应性评估，不能当作动效时长；Apple HIG 的 motion 文档面向 Apple 平台设计，本文将其作为交互设计原则参考。具体 CSS 时长、键盘细节、屏幕阅读器播报和大书签集合表现仍需在实现阶段结合产品和设备实测。
