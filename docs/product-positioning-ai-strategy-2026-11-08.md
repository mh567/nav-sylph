# Habu 产品定位与 AI 演进建议

> 历史研究或设计：2026-11-08 已确定拆分 Habu 与 Pabu，当前边界见 [产品边界](product-boundaries.md)。本文不再作为当前开发规格。


日期：2026-11-08。状态：调研建议，尚未作为开发规格或已批准路线。

用户目标：个人长期使用，并吸引同类用户部署。研究基线：本地 main，HEAD `5380718`，版本 `2.2.16`。本轮核对仓库文档、相关实现和外部一手资料，没有进行用户访谈、同类产品上手测试或目标服务器验证。

## 1. 建议结论

Habu 当前宜定位为：**面向有自主部署能力、需要跨设备使用多个工具的人，提供可自托管的个人工作入口。集中常用链接、资料与轻量状态，帮助用户迅速开始和继续自己的事情。**

对外一句话可采用：**把常用工具、重要资料和正在做的事，放在自己的入口里。**

“个人工作入口”约束产品需要解决的任务；“自托管”说明所有权与部署方式；“导航页”保留为容易理解的使用形态。AI 是逐步改善资料查找与工作衔接的能力，不宜提前成为必须配置的基础依赖。

首批服务个人部署者，兼顾其愿意邀请的少量使用者。公开访问、匿名本地配置、口令同步都保留，但作为入口和便利能力。暂不把公开托管导航服务列为同等产品主线。

长期假设：Habu 可以成为用户自己掌握的工作上下文和交接点，让人和不同助手按授权读取资料、接续进展、回存结果。其价值需要通过真实重复使用证明，不能宣称已经独一无二或人人必需。

## 2. 定位混乱来自哪里

### 2.1 用户与功能的归属不一致

README 的首句仍是极简个人导航与书签页，但功能同时覆盖普通访客、部署者私人工作以及实例治理。当前产品事实上存在三层：

| 层次 | 当前事实 | 定位含义 |
| --- | --- | --- |
| 访客入口 | 默认首页、本地导航、个人引擎、公开模块偏好、口令同步 | 无账号即可开始使用的轻量入口 |
| 部署者私人空间 | 收藏库、备忘待办、私人时间线、服务器监控、WebDAV | 主要完整体验只属于部署者 |
| 实例管理 | 默认模板发布、邀请码、空间停用、容量治理 | 为公开暴露服务承担管理成本 |

证据见 `README.md` 的普通导航、同步、收藏和模块章节，`docs/architecture.md` 的认证与模块边界，以及 `lib/sync-store.js` 的空间读写。普通空间同步导航和允许的模块偏好，不同步管理员收藏库及私人模块。

因此，“任何人都能使用完整个人工作台”超出了现有事实。管理员同时承担实例维护者和唯一完整私人用户的角色；未来若支持多个完整私人用户，需要另行设计数据归属与授权。

### 2.2 两套链接缺少明确关系

首页导航链接与导入收藏库是两份独立数据。前者适合高频打开，后者适合资料积累。这个区分有用，但目前缺少从收藏到首页、从资料到当前事项的连续使用路径。

优先补充选择性关联和操作路径，保留原有数据。不要仅因定位讨论就合并数据库、去掉隐私边界或重写模块平台。

### 2.3 扩展围绕卡片增长，用户目标尚未串联

监控、备忘、时间线各自成立，放在同一页仍可能彼此独立。后续需要用真实工作场景组织：一个项目关联入口、资料、下一步与服务状态。现有架构文档也提出围绕同一资产组织信息，但明确统一资产模型尚未实现。

## 3. 外部产品给出的信号

核对日期为 2026-11-08。以下是官网或官方文档所描述的能力，未实测其效果、部署成本和质量。完整的七产品研究、证据和未知见 [同类产品调研](product-positioning-market-research-2026-11-08.md)。

| 产品方向 | 代表及已提供的价值 | 对 Habu 的含义 |
| --- | --- | --- |
| 自托管仪表盘 | [Homepage](https://gethomepage.dev/) 提供服务与信息组件；[Glance](https://github.com/glanceapp/glance) 聚合订阅与状态 | 增加卡片数量难以形成清楚差异 |
| 资料收藏 | [Karakeep](https://docs.karakeep.com/) 已覆盖 AI 标签、摘要、全文与语义搜索、归档和多端采集 | 自动整理书签是已有竞争类别 |
| 成熟书签管理 | [Raindrop](https://raindrop.io/) 提供集合、标签、检索、归档和跨端使用 | 普通用户会比较完整采集和找回体验 |
| 个人操作入口 | [Raycast AI](https://www.raycast.com/core-features/ai) 强调工具执行、项目上下文与自动化 | 搜索框加聊天窗口的差异有限 |
| 面向助手的接口 | [Karakeep MCP](https://docs.karakeep.com/integrations/mcp/) 支持收藏读写；[Homepage MCP](https://gethomepage.dev/configs/mcp/) 支持读取、校验并按设置修改配置 | MCP 是接入方式，单独提供协议不构成护城河 |

研究推断：值得验证的切口是自托管用户跨工具、跨设备、跨助手时的工作连续性。当前资料不能证明这一切口无人覆盖，也不能证明用户会为其部署 Habu。

## 4. 三条路线的取舍

| 路线 | 核心用户任务 | 对当前项目的新增负担 | 建议 |
| --- | --- | --- | --- |
| 公开口令同步导航 | 随处取得同一份链接 | 获客、服务可靠性、滥用治理、空间恢复与隐私沟通 | 保留现有能力，暂不作为增长主线 |
| 综合极客仪表盘 | 一页看服务、订阅和待办 | 持续维护第三方集成与平台兼容 | 保留精选模块，控制扩展范围 |
| 个人工作入口 | 找到当前事情需要的资料，迅速继续 | 小型场景组织、资料关联、交接记录与受限接口 | 推荐主线，先验证最小闭环 |

以上为基于用户目标与当前结构的定性判断，没有市场规模、增长率或需求评分数据。

不必立刻拆成不同产品，也不必去掉普通同步。对外介绍只保留一个主承诺，其他功能说明它如何支持这个承诺。若未来确有公开托管需求，可复用技术再设计服务方案。

## 5. 现有功能如何归位

| 功能 | 建议角色 | 后续边界 |
| --- | --- | --- |
| 导航、搜索、收藏 | 核心能力 | 导航放常用入口，收藏积累资料；逐步支持显式关联 |
| 本地保存、口令同步 | 使用便利与分发能力 | 维持轻量范围，不自动升级为完整多租户私人空间 |
| 临时文本分享 | 高频小工具和对外协作出口 | 保持临时性；长期保留必须由用户主动另存 |
| 备忘、待办 | 继续工作的线索 | 只做轻量下一步，不扩展成完整项目管理系统 |
| 主机监控 | 自托管人群的状态线索 | 先只读、提供来源与采集时间，不扩展为自动运维平台 |
| 时间线、订阅 | 可选输入 | 与事项有关时才进入主视图，避免持续增加信息噪声 |
| 公开首页 | 体验与分享入口 | 从部署者私人空间显式发布，保持独立权限 |
| AI | 可选的检索与衔接能力 | 没有模型配置时，核心入口仍然完整可用 |

口令同步当前只对口令派生连接证明，配置在服务端以 JSON 内容存储，不能宣传为端到端加密。临时文本分享的浏览器加密属于另一套协议。未来若存入更敏感的个人上下文，应先决定信任模型及恢复方式，再扩大数据范围。

## 6. AI 结合优先解决三件事

### 6.1 帮人找回，而非要求记住标题

场景：“之前收藏的、讲 Keycloak 登录回调问题的那篇资料在哪？”

先把现有关键词检索、标签、人工描述和来源做好，再用少量真实模糊查询比较语义检索是否有增益。仅有 URL 与标题时，模型无法稳定理解文章细节。全文抓取、正文清洗、更新和索引均有成本，不能跳过内容基础直接承诺问答。

返回原始链接及能解释匹配的证据。找不到时明确表示未找到。模型不能凭空补出用户“收藏过”的内容。

### 6.2 让不同助手接着做

场景：用户把一个实际事项的资料、当前进展和下一步交给桌面上的助手，之后换到另一设备或助手继续。

第一版可直接导出可读 Markdown：目标、用户选定的资料链接、最近确认的结论、尚待验证的事项和下一步。无需先做模型路由、多智能体调度或全量自动记忆。

用户整理和确认的信息作为稳定上下文。助手生成的摘要与建议单独标明来源和状态，不能默认为既定事实。成果先进入待确认记录，用户接受后再更新当前进展。

当这种手动交接确有重复使用，再增加受限 API 或 MCP。个人上下文存储独立于某个模型，可以降低更换助手时的重建成本；不同助手的兼容性仍需逐个验证。

### 6.3 解释与当前事项有关的变化

场景：部署者回到某个项目，看到相关服务最近采集状态、未完成事项，以及上次的停留点。

先用规则汇总确定事实，再评估是否需要模型归纳。只显示有来源、时间和明确关联的信息；数据过期与状态未知必须与异常区分。

运行任意命令、修改生产配置、自动修复故障均不进入早期范围。现有监控采集 agent 与未来 AI 智能体需要在文档和界面中清楚区分。

## 7. 一个值得先做的完整场景

以“维护自己的 NAS 与服务”为首个试验事项：

1. 用户选择现有导航与收藏，加入“家庭服务维护”场景。
2. 显示服务入口、关联资料、用户填写的当前进展与一条下一步。
3. 关联已有只读监控时，显示状态及采集时间。
4. 用户导出该场景的上下文，交给自己常用的助手。
5. 助手协助后，用户把结果另存为待确认记录，接受后更新进展。
6. 用户次日在另一设备打开该场景，能够知道接着做什么。

这是待验证的产品体验，当前仓库尚未完整实现。第一版只需要一个场景、少数引用和一份进展记录。书签、监控数据保留原存储，新增部分引用其稳定标识。按现有权限服务部署者本人，不先进行所有私人模块的多用户改造。

也用一个无服务器场景检验方向，例如“学习身份认证”：资料、实验入口、已验证结论和下一次实验。若价值只在看主机状态时成立，则应将人群收窄为自托管服务维护者。

## 8. 最小演进次序与进入条件

以下时间为单维护者的试验节奏建议，不能视为工程排期承诺。

| 阶段 | 最小交付 | 验证重点 | 暂缓 |
| --- | --- | --- | --- |
| 第 1 阶段，约 2 周 | 对外定位草案；记录真实查找与继续工作的过程；少量同类用户访谈 | 哪些任务反复发生，当前替代方案哪里中断 | 大改首页、改存储模型、扩大模块列表 |
| 第 2 阶段，约 2 至 4 周 | 单个场景关联链接与进展；Markdown 上下文导出；手动回存 | 能否完成一次跨设备或跨助手继续工作 | 内置通用聊天、多模型配置中心 |
| 第 3 阶段，验证后投入 | 小范围只读检索 API/MCP；按实测决定语义检索 | 实际助手能否按授权获取相关信息；检索是否优于现状 | 任意工具执行、生产环境写入 |
| 第 4 阶段，持续使用后 | 受限追加记录、结果待确认、少量只读变化摘要 | 复用频率、确认成本、撤销与导出是否可靠 | 全自动代理平台、插件市场、多租户全面扩张 |

阶段之间按证据进入。若场景组织没有反复使用，就保持轻量导航，修复更直接的查找与采集问题。若只需要把收藏交给助手，应优先比较接入 Karakeep 等现有工具，避免重做完整资料平台。

## 9. 技术与隐私的必要约束

这些是未来功能的设计要求，不能视为当前已经实现。

- 沿用服务端权限边界。普通同步口令、管理员会话、未来智能体凭据互不替代。智能体凭据按数据范围及动作授权，可独立撤销。
- 第一阶段只读选定场景。后续追加记录需有幂等保护、来源、确认状态；删除和覆盖等动作另设明确授权。
- 不把管理员密码、WebDAV 凭据、主机采集凭据交给模型。监控状态也可能泄露内部信息，应只返回授权过的字段。
- 数据存放位置与推理位置分开说明。自托管存储后调用外部模型仍会发送被选中的资料，需明示范围；关闭 AI 不影响基础使用。
- 外部网页、订阅和助手回写都按不可信数据处理，不能取得执行权限。以后抓取链接时需另行处理内网访问边界与 SSRF。
- 临时分享的过期和加密语义保持原样，不自动纳入索引、长久摘要或智能体记忆。用户主动另存时说明保留范围变化。
- 派生摘要和索引跟随原资料的删除、权限变化与重新索引处理，避免原始内容删除后仍从 AI 接口返回。
- 不为概念统一重写全项目。先明确一个场景记录与现有对象的引用关系，按实际需要追加迁移。

设计参考：[MCP 安全最佳实践](https://modelcontextprotocol.io/docs/draft/tutorials/security/security_best_practices)讨论令牌使用、授权与代理风险；[Ink & Switch 的 local-first 原始研究](https://www.inkandswitch.com/essay/local-first/)讨论离线使用、长期可用和数据控制。引用用于校准边界，不代表 Habu 已符合全部原则。

## 10. 如何判断有价值

先邀请约 5 至 8 位有自托管习惯、也使用 AI 助手的人。这个样本用于发现问题，不能用于估算市场。

每人提供近期真实任务，观察至少两周。重点记录：

1. 找回已保存资料的成功率与耗时，分别比较现有导航、浏览器书签及用户当前方案。
2. 中断后重新进入任务，是否还要重新搜集资料和解释背景。
3. 场景是否由用户主动重复打开，而非仅为配合测试。
4. 导出的上下文有多少被实际使用，哪里需要修改，助手回存结果是否可信。
5. 安装、升级、备份和模型配置是否消耗了超过收益的精力。

可设定内部继续投入条件，例如 5 位试用者中至少 3 位在两周内主动完成至少 3 次同类闭环，并能指出相对原方案节省的具体步骤。这是试验门槛建议，尚无结果，不构成产品市场匹配证明。

不要以首页停留时间、生成摘要数量或模块数量作为核心目标。入口越高效，用户可能越快离开页面。更有意义的单位是成功找回一次资料、接续一次事情或完成一次可追溯交接。

## 11. 尚待验证的关键问题

- 同类用户的高频困难来自资料查找、项目接续，还是单纯多设备导航？
- 用户愿意主动维护简短进展记录吗？若维护成本过高，概念价值也难以兑现。
- 在浏览器原生入口、Raycast 及成熟助手已有项目记忆的条件下，独立入口提供了多少额外收益？
- 有多少上下文必须保留在 Habu，多少只需引用原系统？不要默认汇集所有私人数据。
- 自托管与跨助手可迁移是否足以促使别人部署？目前没有证据。

建议下一步先完成一个真实事项的手动交接样例与少量访谈，再决定首个实现任务。现有公开同步与私人功能无需因本次研究进行迁移。
